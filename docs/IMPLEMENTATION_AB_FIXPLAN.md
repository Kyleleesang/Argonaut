## Ground rules (do not skip)

1. **Live-verify, don't just unit-test.** `cargo test --workspace` is necessary but *not sufficient*. For any item that changes runtime behavior, build the release binary and drive a real devnet (single- or multi-node as noted), because every bug that mattered on this project was found live, not by tests. Use `--network-backend libp2p` on every node (litep2p's request/response was `unimplemented!()`; B-8 worked around this in `prism-network`, but the flag is still the safe default).
2. **Commit after each completed item** (or each coherent group), with a message naming the finding ID. Branch off `Base` if not already on it.
3. **When a fix needs a decision you can't derive** (consensus-safety math, threat-model assumptions), stop and ask the user rather than guessing.
4. Update [`IMPLEMENTATION_B_PROGRESS.md`](./IMPLEMENTATION_B_PROGRESS.md) / [`IMPLEMENTATION_A_PROGRESS.md`](./IMPLEMENTATION_A_PROGRESS.md) and this doc as items land, so all three stay the source of truth.
5. **Don't trust a piped `cargo test`'s exit code.** `cargo test --workspace 2>&1 | tail -N` reports `tail`'s exit code, not `cargo test`'s — reads as `0` even when a test failed. Check the actual `test result: ... FAILED` lines, or redirect to a file and check `$?` there.

**B-1/AF-4 live-verified for real, 2026-07-07 — and a genuine bug found + fixed in the process.** First actual two-node run of this devnet. Byte-identical `chain_getBlockHash` confirmed across both nodes for levels 0–5 (full 32-byte hash, not just the short display form) — B-1's own acceptance criterion, never run before this session. Along the way, restarting node2 after it fell behind (to test B-7) hit a real, previously undiscovered bug: `node/src/bridge.rs` attached the leader digest via `BlockImportParams::post_digests`, which only survives on the *authoring* node's trusted self-import (`StateAction::ApplyChanges`, no re-execution). Any other node receiving that block through ordinary Substrate block-sync — exactly what happens on restart or when a new node joins — re-executes it via `PrismBridgeVerifier`'s default `StateAction::Execute`, and `frame_executive::Executive::final_checks`' digest-count `assert_eq!` panicked (`wasm unreachable` trap) every time, because `initialize_block`'s `extract_pre_digest` only preserves `DigestItem::PreRuntime` items, silently dropping the `Other`-tagged leader digest during re-verification. **Meaning: any node that ever fell behind the Substrate chain could not safely rejoin the network at all.** Fixed by switching the digest to `DigestItem::PreRuntime` (`LEADER_DIGEST_ENGINE_ID = b"prsm"`), set *before* block-building via `BlockBuilderBuilder::with_inherent_digests` instead of after via `post_digests` — this variant survives identically through `initialize_block` whether the block is being authored or re-verified. Re-verified live after the fix: killed node2, let node1 advance to a level node2 hadn't seen, restarted node2 — it replayed its own DB (B-7), reconnected, backfilled the DAG (B-6, logged `backfill: N unknown hash(es)`), and its log showed `🏆 Imported #5 (...)` (a peer-authored block, not self-mined) with the hash matching node1's byte-for-byte. No panic. This is the AF-4 "determinism choke-point" concern materializing as a real bug, exactly as that finding warned, and it's now closed rather than just diagnosed.

**Deliberately not "fixed," by design, not open work:**
- **B-3**: the paper's exact `δ_d`/`k_min` (Appendix E.1 eq. 31) exist as `paper_k_min`/`paper_delta_d` in `client/prism-ledger/src/confirmation.rs` but are **not** the default — the literal `k_min` is thousands of blocks deep for any sane β (an asymptotic-proof artifact) and would make stage-2 *slower* than stage-1. `ConfirmationParams::default()` keeps the practical placeholder. Don't switch the default without re-deriving a usable operating point first.
- **B5 pruning's two accepted bounded leaks** (documented in `PrismChain::prune`'s doc comment): abandoned-fork `voter_meta` predating the frontier isn't swept (only the live tip's ancestry is walked), and non-canonical sibling proposers at a confirmed level keep their bodies (only the leader's subtree is walked). Both would need a reverse index this port doesn't maintain — same category as B-3's `k_min`.

Root cause: `substrate-wasm-builder` mirrors whatever Cargo features are active on `argonaut-runtime`'s own native build into the separate wasm build it spawns (confirmed by inspecting `target/release/wbuild/argonaut-runtime/Cargo.toml`, which explicitly listed `"dev-signatures"`), and `node/Cargo.toml` was unconditionally requesting that feature on the runtime dependency — needed at the time because `chain_spec.rs`'s dev-account funding went through the feature-gated `ArgonautSigner::Sr25519` path. So every node build, including "production," silently leaked it into the wasm blob; the doc's earlier "confirmed via build.rs" claim had never actually been tested. Fixed: `chain_spec.rs` now derives dev accounts via `sp_core::AccountId32: From<sr25519::Public>` directly (byte-identical result, no dependency on Argonaut's own signer types); `node/Cargo.toml`'s `dev-signatures` is now a real, off-by-default feature; `node/src/benchmarking.rs` (the only other native code needing `Sr25519`) and its two call sites in `command.rs` are gated behind it, mirroring the existing `Storage` benchmark pattern. `cargo test --workspace` green after the change. Re-verified live: rebuilt release, confirmed `target/release/wbuild/argonaut-runtime/Cargo.toml` no longer lists `dev-signatures`, submitted the same sr25519-signed extrinsic — `TaggedTransactionQueue_validate_transaction` now traps (`wasm unreachable`, a SCALE decode failure since the wasm enum only has 2 variants), correctly surfaced as an RPC error, and the node process itself survived untouched (wasm sandbox contains the trap; still mining, RPC still responsive) — not a DoS vector, standard Substrate wasm-execution behavior for any malformed runtime-API call.
- [x] B-2: confirm retargeting moves the observed block interval toward `target_interval_ms` on a running devnet — **done 2026-07-08**, single-miner fresh-DB run. Solo mining started far below the combined target (~50s/block observed vs. the 1000ms combined target across all m+2 slots) since `Params::testnet()`'s initial difficulty guess wasn't calibrated to this machine's real hash rate. Once the first `RETARGET_WINDOW` (20 blocks) elapsed and the first retarget decision fired, the rate visibly corrected: a burst of 13-14 blocks logged within the same second, then oscillating between fast bursts and multi-second gaps as the ±4x-per-window clamp worked through several correction cycles — textbook rolling-window-retarget behavior recovering from a large initial miscalibration (same shape as Bitcoin's own retarget settling after a large hash-rate change), not yet fully converged to a steady 1-block/combined-second cadence within the observed window but unambiguously moving in the right direction and by the right order of magnitude. Did not additionally run a controlled single-miner-then-second-joins comparison given time already spent reaching the first correction; the observed before/after around the first retarget point is itself the core claim this item asks for.
